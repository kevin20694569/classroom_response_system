# 課堂搶答系統 (Classroom Response System) Constitution

本專案為「軟體工程期末專題：課堂搶答系統」(SpecKit 組)，採 AI 代理開發
(Spec-Driven Development)：程式碼與文件由 AI 代理產生，組員負責審閱與驗證。

**專案背景與目標**

- 目標是把課堂上用填空式學習單 (Guided Notes，以 Google Sheets 形式提供) 進行的搶答活動
  搬到線上，讓老師與學生在本機模擬環境就能完成整個活動流程。
- 最優先的是先完成核心功能，而且正確、可以展示；延伸功能只預留擴充點，spec 尚未定義前
  MUST NOT 實作 (YAGNI)。
- 本組與另一小組 (OpenSpec 組) 的系統功能 MUST 一致；會改變對外行為的決策 MUST 記錄下來，
  方便與另一小組同步。

**撰寫慣例**

- 所有文件 (constitution、spec、plan、tasks) MUST 使用繁體中文撰寫；程式碼的識別字與檔名
  MUST 使用英文。
- 本文件只規範跨功能的大原則，具體功能需求以各子功能的 spec 為準。
- 文中 MUST / MUST NOT 為強制要求；SHOULD 為強烈建議，若不遵守須在 plan 中說明理由。

## Core Principles

### I. 伺服器為唯一真實來源 (Server-Authoritative)

- 系統狀態、使用者提交的資料，以及任何先後順序的判定，MUST 由伺服器決定並保存；
  MUST NOT 信任客戶端送來的時間、順序或結果。
- 並發請求 MUST 得到確定、可重現的處理結果，設計時 MUST 明確處理競態條件。
- 權限與資料可見性規則 MUST 在伺服器端強制執行：使用者不該看到的資料，伺服器就
  MUST NOT 傳給該客戶端，不能只靠前端隱藏（例如：活動結束前，MUST NOT 把其他組的作答
  傳給學生端）。

**Rationale**：搶答的公平性取決於先後判定與資料可見性。客戶端時間可被竄改、網路延遲
不一致，前端隱藏的資料也能從開發者工具看到；唯有由伺服器裁決並過濾傳送內容，結果才可信
且可重現。

### II. 即時同步與狀態一致

- 所有已連線使用者看到的系統階段 MUST 與伺服器一致，狀態一改變就 MUST 即時推播。
- 使用者重新整理或斷線重連後，MUST 能回到目前正確的狀態與畫面。
- 有生命週期的流程 MUST 以明確的狀態機定義，MUST NOT 出現未定義的狀態轉換。

**Rationale**：課堂活動是多人同步進行的，老師與各組學生若看到不同階段，活動就無法進行。
明確的狀態機讓狀態轉換可審查、可測試，也讓重連後的畫面還原有唯一依據。

### III. 資料驅動的外部文件處理

- 讀寫 Guided Notes MUST 依文件內容動態定位題號與填空格，MUST NOT 寫死儲存格座標或列號
  （例如固定寫入 C19）。課程助教會使用另一份 Guided Notes 測試，系統 MUST 能處理內容或
  版面不同的文件。
- 定位規則 MUST 以課程提供的官方範本格式為基準；若需要在範本上加入額外標記或佔位符，
  該標記規則 MUST 寫進文件，並在無法辨識時給出明確錯誤，而非默默產生錯誤結果。
- 匯入的資料 MUST 先完整驗證再寫入系統：格式不符時 MUST 給出看得懂、並指出問題位置的
  錯誤訊息，而且 MUST NOT 留下只寫了一半的資料。
- 寫回外部文件時 MUST 只修改目標位置，MUST NOT 破壞原文件的其他內容。

**Rationale**：驗收時會換用不同的 Guided Notes，寫死位置的實作必然失敗。先驗證再寫入、
只改目標位置，可避免系統資料半套或破壞老師原本的教材。

### IV. 模組化與可擴充設計

- 領域邏輯 MUST 與傳輸層 (HTTP / 即時通訊) 及外部服務存取層分離，讓核心邏輯不需網路與
  外部服務就能測試。
- 已知的延伸方向 SHOULD 用介面或策略模式預留擴充點，但核心階段只實作預設行為。目前已知
  方向：題目單位由單題擴充為題組、搶答判定與排名策略可替換、匯出格式可擴充（如 CSV）。
- MUST NOT 過度設計：只有已知會擴充的地方才建立抽象層，並 MUST 在 plan 中寫明理由。

**Rationale**：分層讓核心規則可以快速、穩定地自動化測試；只在已知擴充點預留介面，
兼顧日後延伸與目前「先完成核心功能」的優先順序。

### V. 型別安全與前後端契約 (Type-Safe Contracts)

- 前端、後端與測試 MUST 全部使用 TypeScript，並啟用 strict 模式。
- 前後端共用的資料結構（API 請求與回應、即時事件、領域模型）MUST 集中定義在共享模組，
  作為前後端契約的唯一來源，MUST NOT 在兩端重複定義。
- 型別只保證編譯期正確；所有外部輸入（HTTP 請求、即時訊息、匯入文件、環境變數）MUST 在
  執行期做結構驗證，而且驗證規則與型別 MUST 由同一份定義產生或保持一致。
- MUST NOT 使用 `any`；確實無法避免時，MUST 加註解說明理由，並限制在邊界層。

**Rationale**：AI 代理分批產生前後端程式碼時，最容易出現兩端契約不一致。單一來源的共享
型別配合執行期驗證，能在編譯期與執行期同時攔截錯誤，也防止惡意或格式錯誤的輸入進入系統。

### VI. 圖表生成 (Diagram Generation)：PlantUML 設計優先 (Design-First with PlantUML)

**規則（課程指定內容，保留原文）**：

- 規格制定階段 (Specification Phase)：在 speckit.specify 階段，必須使用 PlantUML 語法生成組件圖 (Component diagram)、類別圖 (Class diagram) 和時序圖 (Sequence diagram)。這些圖表檔案 (.puml) 必須儲存在 ./diagrams/ 目錄中。
- 產物生成 (Artifact Generation)：檔案建立後，必須使用 PlantUML CLI (java -jar plantuml.jar "./diagrams/*.puml") 將所有 .puml 檔案轉換為 PNG 圖片，且輸出的圖片必須儲存在相同的目錄中。
- 規劃階段 (Planning Phase)：speckit.plan 階段必須將這些圖表作為主要藍圖，用以生成應用程式的架構與組件。
- 實作階段 (Implementation Phase)：在 speckit.implement 階段完成程式碼生成後，必須執行驗證步驟，以確保最終的程式碼與圖表完全一致。

**補充規則**：

- 圖表檔名 MUST 以子功能編號開頭（例如 `001-xxx-sequence.puml`），避免不同子功能互相覆蓋。
- 若環境以套件管理器安裝 PlantUML，可用等效指令 `plantuml "./diagrams/*.puml"` 轉檔。
- `.puml` 與 `.png` 都 MUST 納入版控。
- 實作若必須偏離圖表，MUST 先更新圖表並重新產生 PNG，再修改程式碼。

**Rationale**：課程要求以圖表作為設計的主要藍圖。先畫圖再實作，讓組員能在寫程式之前審閱
架構與互動流程；要求圖表與程式碼一致，避免文件與實作脫節。

### VII. 測試與驗證標準

- 每個功能 MUST 至少有一個正常案例和一個邊界或錯誤案例的自動化測試。
- 涉及並發、權限或資料可見性的規則，MUST 有專門的自動化測試證明它們成立。
- Guided Notes 的匯入與匯出 MUST 用至少兩份版面不同的測試文件驗證，證明沒有寫死位置；
  測試文件的題目一律設計為簡答題。
- 自動化測試 MUST NOT 依賴真實的外部服務或真實憑證；外部服務一律以本機測試資料或替身
  (mock / fake) 取代。
- 除了 AI 自動驗證，每個功能 MUST 附上人工驗證步驟清單，涵蓋老師端與至少兩組學生端的
  完整活動流程。
- 每個 Phase 結束時，型別檢查、lint 與測試 MUST 全部通過，並 MUST 回報執行的指令和結果；
  沒有全部通過，MUST NOT 進入下一個 Phase。

**Rationale**：AI 產生的程式碼需要可驗證的證據才能信任。原則 I 與 III 的關鍵保證（並發、
可見性、不寫死位置）只有靠專門測試才能證明；人工驗證清單則確保 Demo 所見與自動化測試一致。

### VIII. 安全與機敏資料

- 密碼、API 金鑰、服務帳號憑證等機敏資料只能放在環境變數或不納入版控的設定檔，MUST NOT
  出現在程式碼、文件、log 或 Git 歷史裡；repo MUST 提供不含真實值的範例設定檔。
- 環境變數 MUST 在啟動時集中讀取並驗證，缺少或格式錯誤就中止啟動，並清楚說明原因。
- 錯誤訊息 MUST 讓使用者看得懂，但 MUST NOT 洩漏內部細節（如堆疊、檔案路徑、憑證）。
- MUST 依角色（老師 / 學生）控管操作權限，學生 MUST NOT 能執行老師專屬的操作。

**Rationale**：存取 Google Sheets 需要服務帳號憑證，一旦進入 Git 歷史就難以徹底移除。
啟動時驗證設定能讓錯誤在第一時間浮現；角色權限則是搶答公平性的基本前提。

## 技術限制與程式碼規範

- **技術棧**：MUST 以 Node.js（LTS 版本，專案以版本檔 `.nvmrc` 固定主版本）搭配
  TypeScript 為核心。具體框架與套件在 plan 階段決定並說明理由。
  理由：系統會拆成多個子功能，各自執行 plan，技術棧必須在此統一，避免各子功能選用不同技術。
- **執行環境**：系統只需在本機運行模擬，不需部署對外伺服器；MUST 能用文件中寫明的
  單一指令在本機啟動。
- **多身分本機模擬**：系統 MUST 支援在同一台電腦上，以多個瀏覽器分頁或視窗同時扮演老師與
  多個不同組別的學生，各分頁的身分 MUST 互不干擾（以便本機模擬與錄製 Demo）。
- **相依套件**：MUST 用 lock file 鎖定版本，MUST NOT 使用已停止維護的套件。
- **程式碼風格**：MUST 統一風格，並用 lint / format 工具自動檢查；模組依功能分層組織，
  對外匯出的函式與模組邊界 MUST 明確標註型別。
- **註解**：重要的領域規則 MUST 有註解，說明它的業務意義。
- **Log**：MUST 使用結構化 log 記錄關鍵事件（狀態轉換、提交與判定結果、匯入匯出結果），
  但 MUST NOT 記錄機敏資訊。

## 開發流程與品質關卡

- **子功能拆分**：系統拆成多個可以獨立交付的子功能，每個子功能各有自己的 spec、plan、
  tasks 與圖表，MUST 在獨立的 Git branch 開發，透過 Pull Request 合併。開始新的子功能前，
  MUST 先確認 `.specify/feature.json` 指向正確的子功能。
- **階段關卡**：每個子功能 MUST 依序通過以下關卡：
  1. specify 後反覆執行 clarify，直到沒有模糊之處，才進入 plan；
  2. tasks 後執行 analyze，直到 spec、plan、tasks 之間沒有衝突或缺漏，才進入 implement；
  3. implement 後執行 converge 補齊遺漏，直到程式碼與文件一致。
- **人工審閱**：AI 產生的 spec、plan、tasks 與圖表 MUST 經組員人工審閱，確認符合需求後
  才進入下一階段；發現問題 SHOULD 及早修正。
- **單一需求依據**：spec 是需求的唯一依據。程式碼、文件（spec / plan / tasks / 圖表）與
  Demo MUST 一致；發現不一致時先判斷是哪一邊錯：需求變了，就先改 spec 與圖表，再改程式碼；
  程式碼寫錯，就直接修程式碼。

## Governance

- 本 constitution 優先於其他開發慣例；spec、plan、tasks 與實作都 MUST 通過 constitution
  檢查（plan 階段的 Constitution Check 與 analyze 階段的一致性檢查皆以本文件為準）。
- 違反原則的設計 MUST 在 plan 中明確列出並說明理由；無正當理由者不得進入下一階段。
- 修訂程序：修訂時 MUST 寫下變更理由，並依語意化版本 (MAJOR.MINOR.PATCH) 更新版本號：
  - MAJOR：移除原則或重新定義原則，造成不相容的治理變更；
  - MINOR：新增原則或章節，或實質擴充既有規範；
  - PATCH：釐清、措辭或錯字修正等不改變語意的調整。
- 影響對外功能的修訂，MUST 同步告知 OpenSpec 小組。
